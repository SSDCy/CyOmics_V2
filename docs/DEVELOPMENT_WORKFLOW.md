# 统一仓库开发流程

1. 每次只实施一个有明确验收条件的小任务，前端、后端、测试各在自己的功能分支提交。
2. 前端以 `frontend/` 为交付边界；Sites 原生工作区保留自己的站点身份。真实 `.openai/hosting.json` 仅保存在本机，不提交到公开仓库。
3. 后端以 `backend/` 为交付边界，数据库与科研数据保持在 A；真实邮箱、密钥、连接信息不得进 Git 或提交历史。
4. 项目经理审查实际差异和测试证据，测试方独立复核后，再由用户验收。自测、源码检查、模拟集成测试、真实 E2E 和人工验收分别记录。
5. `main` 用于已审查版本。A 在与运行目录分开的源码目录获取确认的提交；运行版本保留明确的提交号。不要直接在正在运行的目录执行拉取或覆盖。
6. 获取代码和切换服务分开。拉取代码不自动迁移数据库，不启动/停止/重启服务，不操作旧 Cy_Omics 生产项目。
7. 新的科研算法与正式图表使用已验证 R 包或 R 标准函数；保留版本、参数和来源，不用自行编写算法冒充包的实现。
8. 真实 TXT/FASTA 文件不进公开 Git；使用服务器授权路径进行后续受控验收。公开测试数据保持为合成数据。

## 提交约定

科研数据库和工具的提供方选择统一遵循 [本地优先规范](RESOURCE_PROVIDER_POLICY.md)：
可用本地资源优先，缺少相应能力时才按项目设置使用核实过的官方 API。规范和实现状态分别记录。

提交应包含功能代码、相关测试与必要说明，避免混入生成目录、依赖副本、日志和内部审计快照。提交前检查文件清单、敏感信息和变更范围；不使用强制推送覆盖共享历史。

## A/B 首次接入

B 的统一源码工作区是从本仓库克隆的目录。A 的新源码副本应与既有 releases、runtime、auth-dev、data 分开；确认访问权限和网络后再克隆，不覆盖现有项目文件。初次 A 接入及服务切换完成前，不把代码上传成功描述成部署完成。
